# تقرير بناء AHMED Agent — v0.1 (Vertical Slice)

التاريخ: 2 أكتوبر 2026

## 1. ما تم بناؤه

Monorepo بـ npm workspaces فيه ثلاث حزم:

- **packages/contract**: أنواع TypeScript للعقد، تطابق `V0_CONTRACT.md` حقلًا بحقل. الـCore والتطبيق يستوردانها معًا.
- **apps/core** (Node + TypeScript + Fastify + SQLite):
  - `db.ts`: جداول conversations / tasks / messages / actions / executions / audit_log. جدول الـaudit محمي بـtriggers تمنع UPDATE وDELETE.
  - `stateMachine.ts`: جدول انتقالات صريح، وأي انتقال غير موجود يرمي `InvalidTransitionError`.
  - `store.ts`: كل الكتابة في القاعدة. كل انتقال حالة compare-and-set على الحالة الحالية، ويُسجَّل `STATUS_CHANGED` في الـaudit.
  - `workspace.ts`: التحقق من المسارات: ترفض `..` والمسارات المطلقة وحروف الأقراص، وتتبع الـrealpath لأقرب مجلد موجود، فترفض symlinks/junctions التي تخرج من الـworkspace.
  - `tools.ts`: Tool Registry فيه `read_file` (risk: read: txt/md/pdf) و`move_file` (risk: write: بدون overwrite، وينشئ مجلد الوجهة). لا توجد أداة حذف.
  - `model.ts`: واجهة `ModelClient`، وتطبيق `AnthropicModelClient` (tool use عبر `@anthropic-ai/sdk`)، و`FakeModelClient` للاختبارات.
  - `agent.ts`: الـAgent Core: حلقة النموذج والأدوات، طلب الموافقة، القرار، الحجز، التنفيذ، التحقق من القرص، انتهاء الصلاحية، والاستعادة بعد إعادة التشغيل.
  - `server.ts`: الـAPI الأربعة مع مصادقة Bearer على كل طلب، ورفع ملف multipart إلى `workspace/inbox/`.
- **apps/mobile** (Expo SDK 57 + TypeScript، يعمل على Expo Go): شاشة واحدة سوداء بلمسة ذهبية، فيها:
  - المحادثة، وإدخال النص، وزر اختيار ملف.
  - شارة حالة المهمة، وApproval Card فيها العملية والملف والوجهة والأداة والخطورة ووقت الانتهاء، مع زرّي APPROVE وREJECT.
  - عرض النتيجة مع علامة "✓ verified".
  - Loading / Error / Retry، وقائمة المهام السابقة.
  - polling كل ثانيتين للمهام الجارية، وحفظ `conversation_id` محليًا واستعادة الحالة من الـCore عند الفتح.

## 2. أوامر التشغيل خطوة بخطوة (PowerShell، من `C:\dev\ahmed-agent-v01`)

### الـCore على الكمبيوتر
1. `npm install`
2. `Copy-Item apps/core/.env.example apps/core/.env` ثم افتحه وعبّئ:
   - `APP_TOKEN`: سر طويل. لتوليده: `[guid]::NewGuid().ToString("N") + [guid]::NewGuid().ToString("N")`
   - `ANTHROPIC_API_KEY`: مفتاحك
   - `MODEL_NAME`: افتراضيًا `claude-opus-5-5`
3. `npm run core`: يظهر `AHMED Core listening on http://0.0.0.0:8787`.
4. إذا ظهرت نافذة Windows Firewall، اسمح لـNode على الشبكات الخاصة (Private).
5. اعرف IP الكمبيوتر: `ipconfig`، وخذ IPv4 لمحوّل الواي فاي (مثل `192.168.1.78`).

### التطبيق على الجوال عبر Expo Go
1. ثبّت Expo Go على الجوال (يجب أن يدعم SDK 57، أي آخر إصدار من المتجر).
2. `Copy-Item apps/mobile/.env.example apps/mobile/.env` ثم عبّئ:
   - `EXPO_PUBLIC_CORE_URL=http://192.168.1.78:8787` (ضع IP جهازك)
   - `EXPO_PUBLIC_APP_TOKEN=` نفس قيمة `APP_TOKEN`
3. في نافذة PowerShell ثانية: `npm run mobile`
4. امسح رمز QR: على Android من داخل Expo Go، وعلى iPhone بالكاميرا. الجوال والكمبيوتر على نفس الواي فاي.
5. بعد أي تعديل على `apps/mobile/.env` أوقف Expo وأعد تشغيله.

### الاختبارات
- `npm test`
- `npm run typecheck` و`npm run typecheck -w @ahmed/mobile`

## 4. القرارات التقنية

1. **تشغيل TypeScript مباشرة بـtsx** بدون خطوة build، أبسط على Windows.
2. **better-sqlite3 13 يأتي بملفات binary جاهزة لـWindows**. npm 11 أوقف install scripts لـbetter-sqlite3 وesbuild، ولم أوافق عليها لأن الحزمتين تعملان بدونها (تحققت من ذلك). لا node-gyp ولا أدوات بناء ولا صلاحيات مدير.
3. **المعالجة غير متزامنة**: `POST /v1/messages` يرجع فورًا `202 TASK_STATUS`، والنموذج يعمل في الخلفية، والتطبيق يعمل polling. لا اتصال يبقى مفتوحًا.
4. **كل رسالة = مهمة**. الرد بدون أداة ينتهي COMPLETED بنوع MESSAGE، والرد بأداة بنوع RESULT.
5. **الموافقة والحجز في transaction واحدة**: تسجيل القرار (فقط إذا لم يوجد قرار سابق)، ثم WAITING→APPROVED، ثم إدخال صف في `executions` بمفتاح `idempotency_key` UNIQUE، ثم APPROVED→EXECUTING. وقبل التنفيذ يُتحقق مرة أخرى من تطابق task_id وaction_id وidempotency_key ومن أن القرار سُجّل قبل الانتهاء.
6. **كل تنفيذ يمر بـVERIFYING، والقرص هو المرجع**. COMPLETED فقط إذا اختفى الملف من المصدر وظهر في الوجهة.
7. **انتهاء الصلاحية بدون مؤقتات**: يُفحص عند القرار، وعند GET للمهمة أو المحادثة، وعند بدء التشغيل. القرار بعد الانتهاء يرجع 410 والمهمة REJECTED.
8. **انتقالان إضافيان للفشل**: RECEIVED→FAILED وPROCESSING→FAILED، لأخطاء النموذج وللرسائل التي قطعتها إعادة التشغيل (`INTERRUPTED`). كل الانتقالات الأخرى كما في الأمر حرفيًا.
9. **أخطاء الأدوات نوعان**:
   - قاتلة تُنهي المهمة فورًا بـERROR واضح: `PATH_OUTSIDE_WORKSPACE` و`UNSUPPORTED_FILE_TYPE`.
   - عادية تُعاد للنموذج ليشرحها: ملف غير موجود، أو ملف بنفس الاسم في الوجهة.
10. **فحص التعارض قبل طلب الموافقة أيضًا**: إذا كانت الوجهة فيها ملف بنفس الاسم، لا يُطلب من أحمد الموافقة على عملية ستفشل. والفحص يتكرر عند التنفيذ.
11. **request_id يمنع التكرار**: زر Retry في التطبيق يعيد إرسال نفس request_id، فلا تتكرر المهمة.
12. **اسم الملف المرفوع من JSON الـpayload**: لأن ترميز اسم الملف في رأس multipart غير مضمون UTF-8، ولهذا تعمل الأسماء العربية. عند تكرار الاسم يُضاف `-1` ولا يُستبدل ملف موجود أبدًا.
13. **ذاكرة المحادثة**: تُحفظ رسائل النص لكل conversation_id مع ملاحظة بمسار المرفق في الـworkspace، وهذا ما يجعل "انقل الملف" يُفهم بعد التلخيص. تبادلات الأدوات داخل المهمة لا تُحفظ بين المهام.
14. **PDF عبر unpdf**: JavaScript خالص بدون native modules.
15. **النموذج**: `claude-opus-5-5` افتراضيًا في `.env.example`، و`max_tokens: 16000`. حالة `refusal` تُعامل كخطأ نموذج واضح. ولم أضف fallbacks أو إعدادات thinking لأنها غير لازمة للـSlice.
16. **حد النص للنموذج 150 ألف حرف** مع ملاحظة صريحة بالقطع إن حصل، وليس قطعًا صامتًا.
17. **حذفت من قالب Expo**: `.claude/settings.json` لأنه يفعّل plugin، وهذا يخالف قاعدة "لا كونكترات ولا MCP"، وكذلك `AGENTS.md` و`LICENSE`.
18. **هوية git للمستودع فقط**: الاسم Ahmed مع بريدك. لم تتغير إعدادات git العامة، ولم يتم أي push.
19. **اعتماديات التطبيق**: `expo-document-picker` و`@react-native-async-storage/async-storage` فقط، عبر `npx expo install`. كلاهما مدعوم في Expo Go.

## 5. القيود المعروفة

- **الاختبارات الآلية كلها بـFakeModelClient**. مسار Anthropic الحقيقي مُختبر يدويًا فقط (القسم 7)، ولا يوجد له اختبار آلي.
- **الاتصال HTTP غير مشفر على الشبكة المحلية**، فالـtoken يمر نصًا واضحًا على الواي فاي.
- **`EXPO_PUBLIC_APP_TOKEN` مضمّن داخل حزمة التطبيق**، ومن يملك الحزمة يستطيع استخراجه. هذا مقبول لاستخدام شخصي على شبكة منزلية فقط.
- **نافذة صغيرة جدًا (TOCTOU) بين فحص وجود الوجهة وتنفيذ `rename`**. على Windows، `rename` يستبدل الملف الموجود، فلو أُنشئ ملف بنفس الاسم في تلك اللحظة بالذات قد يُستبدل.
- **الـPDF الممسوح ضوئيًا (صور) لا يعطي نصًا**، لا يوجد OCR.
- **الحدود**: حجم الرفع 25MB، ونص الملف للنموذج 150 ألف حرف.
- **الرسالة التي كانت قيد المعالجة عند إعادة تشغيل الـCore** تصبح FAILED/INTERRUPTED ويجب إرسالها مرة أخرى.
- **بطاقة الموافقة لا تُحدَّث تلقائيًا عند انتهاء صلاحيتها**، لأن الـpolling للمهام الجارية فقط. عند الضغط بعد الانتهاء يرجع الـCore 410 وتتحدث الشاشة إلى REJECTED. و"الدقائق المتبقية" تُحسب من ساعة الجوال.
- **محادثة واحدة لكل جهاز**: لا زر "محادثة جديدة"، ولا pagination للرسائل.
- **الاختبار اليدوي تم على iPhone فقط** عبر Expo Go (القسم 7). لم يُختبر التطبيق على Android على جهاز حقيقي.
- **لا tunnel**: يجب أن يكون الجوال والكمبيوتر على نفس الشبكة.
- **`npm audit` يُظهر 12 تنبيهًا** في اعتماديات أدوات Expo، ولم أعالجها لأنها خارج نطاق الـSlice.
- **سلوك النموذج الحقيقي** (متى يستدعي أي أداة) يعتمد على الـsystem prompt في `agent.ts`. الصلاحيات نفسها تحكمها الـRegistry في الكود وليس النموذج.

## 6. خطوات الاختبار اليدوي للسيناريو كاملًا من الجوال

1. شغّل الـCore (`npm run core`) ثم التطبيق (`npm run mobile`)، وافتح التطبيق في Expo Go. يجب أن يظهر عنوان الـCore أسفل "AHMED Agent" بدون شريط خطأ.
2. **التلخيص**:
   - اضغط 📎 واختر ملف `.txt` أو `.md` أو `.pdf`، واكتب: "لخص لي هذا الملف."، ثم Send.
   - يظهر "Working…" مع شارة PROCESSING، ثم يصل الملخص وتصبح الشارة COMPLETED.
   - على الكمبيوتر: الملف موجود في `apps/core/workspace/inbox/`.
3. **طلب النقل**:
   - اكتب: "انقل الملف إلى مجلد archive."
   - تظهر Approval Card فيها: Operation `move_file`، وFile `inbox/<اسم>`، وDestination `archive/<اسم>`، وTool، وRisk `WRITE`، ووقت الانتهاء. والشارة `WAITING FOR APPROVAL`.
   - على الكمبيوتر: الملف ما زال في inbox، ولا يوجد مجلد archive.
4. **الرفض**: اضغط REJECT. تظهر رسالة "Rejected… Nothing was changed."، والشارة REJECTED، والملف لم يتحرك.
5. **الموافقة**:
   - اطلب النقل مرة أخرى، ثم اضغط APPROVE.
   - تظهر رسالة "Done: moved … Verified on disk." مع "✓ verified"، والشارة COMPLETED.
   - على الكمبيوتر: الملف في `apps/core/workspace/archive/` ولم يعد في inbox.
6. **إعادة الفتح**: أغلق التطبيق تمامًا وافتحه. تعود المحادثة والمهام كما هي، وزر "Tasks" يعرض كل المهام بحالاتها.
7. **إعادة تشغيل الـCore أثناء انتظار موافقة**:
   - ارفع ملفًا جديدًا واطلب نقله، ولا توافق.
   - أوقف الـCore (Ctrl+C) وشغّله من جديد.
   - في التطبيق ما زالت البطاقة موجودة، وAPPROVE يعمل وينفذ مرة واحدة.
8. **فشل التنفيذ**:
   - ارفع ملفًا بنفس اسم ملف موجود في archive، واطلب نقله.
   - يجب أن يرد الوكيل بأن الوجهة فيها ملف بنفس الاسم، بدون طلب موافقة.
   - بديل: أثناء انتظار الموافقة ضع يدويًا ملفًا بنفس الاسم في archive ثم اضغط APPROVE. النتيجة ERROR / FAILED، والملفان لم يتغيرا.
9. **المصادقة**: من الكمبيوتر نفّذ `Invoke-WebRequest http://localhost:8787/v1/conversations/x`. النتيجة 401.
10. **السجل**: افتح `apps/core/ahmed-core.db` بأي عارض SQLite، وراجع جدول `audit_log` للمهمة. يجب أن يحتوي الأحداث بالترتيب، من REQUEST_RECEIVED إلى TASK_COMPLETED.

### مشكلة ظهرت أثناء الاختبار وتم إصلاحها
- **العَرَض:** على iPhone، بعد اختيار ملف بزر 📎 لم يكن الإرسال يعمل. لم يصل أي طلب للـCore، ولم يظهر سبب واضح.
- **السبب:** Expo SDK 57 يستبدل `fetch` بـ`expo/fetch`، وهو يرفض صيغة React Native القديمة لجزء الملف `{ uri, name, type }` ("Unsupported FormDataPart implementation")، فلا يُرسل الطلب أصلًا. وكان التطبيق يعرض بدلها رسالة عامة.
- **الإصلاح:**
  - إرسال الملف كـ`File` من `expo-file-system`.
  - عرض سبب الخطأ الحقيقي على الشاشة.
  - زر الإرسال لم يعد يتعطل بصمت.
  - الـCore يسجل الطلبات المرفوضة في الـaudit (`REQUEST_REJECTED`).
  - أُضيفت اختبارات لشكل الطلب الذي يرسله `expo/fetch`، ولملف PDF بعدة ميغابايت بدون نص.

## 8. إصلاح التحقق من النقل وانتهاء الموافقة — 20 أكتوبر 2026

الإصلاح على فرع `fix/core-move-verification` المبني من `main`، ولا يدمج فروع الذاكرة والأدوات أو يغيّر إعدادات جهاز أحمد.

### الأخطاء المثبتة والإصلاح

- كان اختفاء المصدر ووجود أي ملف باسم الوجهة كافيًا لعرض `COMPLETED` و`verified=true`، حتى بعد تسجيل فشل التنفيذ أو عند الاستعادة بعد إعادة التشغيل. يُحفظ الآن SHA-256 لمحتوى المصدر مع طلب الموافقة، وتُفحص البصمة قبل النقل وبعده. لا يُقبل ملف آخر في الوجهة، حتى لو كان له الحجم نفسه.
- أصبح سجل `EXECUTION_ERROR` المحفوظ لنفس العملية يمنع إعلان نجاحها، بما في ذلك بعد إعادة التشغيل. الاستعادة تتحقق فقط ولا تعيد التنفيذ. رسالة الفشل توضّح تعذر التحقق بدل الجزم بأن الملف لم يتحرك.
- كانت الموافقة تُقبل عند لحظة `expires_at` نفسها، وقد يختلف وقت فحص الصلاحية عن الوقت المحفوظ للقرار. تُرفض الآن القرارات التي تصل عند الموعد أو بعده. القرار الذي يصل قبله يستخدم وقت قبول واحدًا للفحص والحفظ، وحارس التنفيذ يشترط `decided_at < expires_at`.

## 9. البث الحي للأحداث `GET /v1/events` — 22 أكتوبر 2026

الفرع `claude/project-modification-suggestions-879mj4`. الاقتراح الأول من ثلاثة اقتراحات، وأحمد طلب بحث في
الممارسات وتجارب المستخدمين قبل التنفيذ.

### البحث والمقارنة

خمس جهات بحث (SSE في بيئات التشغيل، Fastify 5 مع تجارب على النسخة المثبتة، سجل أحداث على SQLite،
العملاء: Expo وUnreal، ومقارنة SSE وWebSocket والـpolling مع الأمان). الخلاصة:

| الخيار | القرار | السبب |
|--------|--------|-------|
| SSE عبر fetch | **مختار** | الاتجاه واحد (الأوامر أصلًا عبر REST)، الاستئناف جزء من البروتوكول، يتجرب بـ`curl -N`، بدون اعتماديات جديدة |
| WebSocket | مؤجل | يحتاج `ws`، والاستئناف والنبض والإغلاق كلها علينا. نرجع له إذا جسر Unreal احتاج تحكم باتجاهين |
| Long-polling | جزئي | `GET /v1/events/page?wait=25` فقط، لأنه أسهل طريق لـUnreal بدون محلل SSE |
| polling كل 2 ثانية | احتياطي | يبقى في التطبيق إذا البث مو شغال |
| `@fastify/sse` | مرفوض الحين | نسخة 0.6.1 قبل 1.0، ومشاكل مفتوحة (#54 تعليق مع backpressure، #57 يعطل الإغلاق) |
| `fastify-sse-v2` | مرفوض | بلاغ حقن حقول SSE مفتوح (#110) وتسريب مستمعين (#112) |
| البث من `audit_log` مباشرة | مرفوض | فيه نص الرسائل والمسارات والخطط، ويصير عقد عام مجمّد |
| جدول `events` منفصل يُكتب في نفس المعاملة | **مختار** | الحدث موجود فقط إذا التغيير حصل فعلًا |

مرحلة التصاميم الثلاثة والحكمين أُلغيت لتسريع التسليم، وعُوّضت بمراجعة متشككة على الكود بعد التنفيذ.

### ما تغيّر

- جدول `events` (append-only بمشغلات) وجدول `meta` فيه `stream_id` عشوائي لكل قاعدة بيانات.
- كل تغيير حالة (إنشاء مهمة، كل انتقال في آلة الحالات، الرسائل، طلب الموافقة وقرارها، التحقق) يكتب حدثًا
  في نفس المعاملة. البيانات معرفات وحالات فقط: لا نص رسائل ولا أسماء ملفات ولا مسارات ولا خطط.
- `GET /v1/events`: SSE خلف نفس التوكن. الاستئناف بـ`Last-Event-ID` أو `?after=`. التوصيل "جرس ثم سحب
  بالمؤشر": المخزن ينبّه بعد انتهاء المعاملة، وكل اتصال يقرأ `id > cursor`، فلا يُرسل حدث تراجعت معاملته،
  والإعادة والبث الحي نفس المسار (بدون فجوة وبدون تكرار).
- `prev_id` على كل حدث مبثوث يكشف ضياع إطار في الطريق (مشكلة معروفة في expo/fetch على أندرويد).
- تحكم بالتدفق (توقف عند امتلاء المقبس، إغلاق بعد 60 ثانية تعليق)، نبض كل 15 ثانية، عمر أقصى 30 دقيقة،
  حد 8 اتصالات (يُغلق الأقدم حتى لا يُحبس الجوال بسبب اتصال ميت)، `stream.reset` إذا المؤشر من قاعدة أخرى،
  و`stream.shutdown` مع `preClose` حتى ينتهي `Ctrl+C`.
- `GET /v1/events/page`: نفس الأحداث JSON، مع `?wait=` حتى 25 ثانية.
- الموافقات تنتهي أيضًا بمؤقت كل 10 ثواني، لأن العميل اللي يسمع البث ما عاد يستدعي القراءات اللي كانت تشغّل الانتهاء.
- التطبيق: `src/events.ts` يقرأ البث عبر expo/fetch، يستأنف بالمؤشر و`stream_id`، مراقب 45 ثانية لانقطاع
  الواي فاي الصامت، تأخير متصاعد مع عشوائية، يقطع في الخلفية ويلحق عند الرجوع، يتوقف عند 401، ويرجع للـpolling
  عند 404. `App.tsx` يحدّث المحادثة عند كل حدث، ويرجع للـpolling كل 2 ثانية إذا البث مو حي. الرأس يعرض Live أو Polling.
- محلل SSE مشترك في `packages/contract/src/sse.ts` لأي عميل TypeScript (منها واجهة Architect Control لاحقًا).
- العقد: القسم 6 في `V0_CONTRACT.md` والأنواع في `packages/contract`. نسخة العقد تبقى `0.1` (إضافة فقط).
