الدور: مرجع يشرح الاتجاه الكامل للنظام. التنفيذ يحكمه ملف الأمر التنفيذي، وعند أي تعارض بينهما الأمر التنفيذي هو الحاكم.

## 1. الواجهة الرئيسية: تطبيق أحمد
التطبيق هو نقطة الدخول الأساسية للوكيل. لا نستخدم Telegram كواجهة للنسخة الأساسية.

من خلاله يقدر أحمد:
- يرسل رسالة نصية.
- يرفع ملفًا.
- يشاهد رد الوكيل.
- يشاهد حالة المهمة أثناء التنفيذ.
- يستقبل طلبات الموافقة.
- يوافق أو يرفض العمليات الحساسة.
- يشاهد نتيجة التنفيذ.
- يرجع إلى سجل المهام السابقة.

لاحقًا (ليس في v0.1): إرسال الصوت، رفع الصور، والمحادثة الصوتية مع الوكيل.

## 2. دور التطبيق
التطبيق ليس عقل الوكيل. وظيفته: User Interface / I/O Layer.
لا يحتوي منطق الوكيل، ولا يتصل بمزود النموذج، ولا يحمل مفاتيح النماذج. يتصل بالـCore مباشرة عبر token خاص به.

التدفق:
Ahmed → Mobile App → Core API → Agent Core → Tools / Models / Retrieval / n8n
ثم تعود النتيجة إلى التطبيق.

## 3. دور Agent Core
النواة هي العقل الحقيقي للنظام. مسؤولة عن:
- فهم الطلب.
- إدارة حالة المهمة.
- اختيار النموذج.
- اختيار الأداة.
- تحديد هل العملية قراءة أم كتابة، من تعريف الأداة في الكود (Tool Registry)، لا من حكم النموذج.
- تحديد هل تحتاج موافقة بشرية.
- حفظ الحالة.
- التحقق من نتيجة التنفيذ.
- تسجيل الأحداث في Audit Log.

هذا المنطق لا يوضع في التطبيق ولا في n8n.

## 4. دور n8n
طبقة Automation / Actions / Integration خلف النظام: Webhooks، GitHub، البريد، الخدمات الخارجية، المهام المجدولة، Workflows، الربط بين الخدمات.
ليس عقل الوكيل، وليس واجهة أحمد، ولا يحفظ حالة المهمة، ولا يغيرها بنفسه. غير مربوط في v0.1.

## 5. الملفات ومساحة العمل
- الملفات التي يعمل عليها الوكيل تعيش داخل مساحة عمل واحدة على الـCore (workspace)، وليس على الهاتف.
- الملف الذي يرفعه أحمد من التطبيق ينتقل إلى الـworkspace، وكل عمليات القراءة والنقل تجري داخلها.
- لا وصول لأي مسار خارج الـworkspace.

## 6. Human-in-the-Loop داخل التطبيق
العمليات الحساسة (Write Actions) مثل: نقل ملف، حذف ملف، تعديل بيانات، إرسال رسالة، تشغيل أمر، تنفيذ Action خارجي.

عندما يقرر الوكيل عملية حساسة:
- النواة تغير حالة المهمة إلى WAITING_FOR_APPROVAL.
- التطبيق يعرض طلب موافقة واضحًا:
  الوكيل يريد نقل الملف report.pdf إلى المجلد archive
  [ موافق ]   [ رفض ]
- APPROVE أو REJECT يُرسل إلى Core API مع action_id نفسه.
- لا يبقى أي اتصال HTTP مفتوح بانتظار المستخدم.
- لكل موافقة صلاحية زمنية، وبعد انتهائها لا تُنفذ.

في v0.1 العملية الحساسة الوحيدة هي نقل الملف. لا حذف من أي نوع في v0.1.

## 7. State Machine
RECEIVED → PROCESSING → WAITING_FOR_APPROVAL → APPROVED / REJECTED → EXECUTING → VERIFYING → COMPLETED / FAILED
- الحالة محفوظة في قاعدة البيانات، لا في ذاكرة السيرفر.
- الانتقالات المسموحة معرّفة صراحة.
- بعد إعادة تشغيل النواة: ما كان قيد التنفيذ يُتحقق منه على الواقع، ولا يُعاد تنفيذه.

## 8. أول Vertical Slice
أحمد يفتح التطبيق، يرفع ملفًا ويكتب: "لخص لي هذا الملف."
النواة تفهم الطلب، تستخدم read_file، ويعود الملخص إلى التطبيق.

ثم يكتب أحمد: "انقل الملف إلى مجلد archive."
النواة تصنفها عملية حساسة، تتحول المهمة إلى WAITING_FOR_APPROVAL، ويظهر طلب الموافقة في التطبيق.

إذا ضغط موافق: النواة تستأنف، تنفذ النقل مرة واحدة، تتحقق أن الملف انتقل فعلًا، تسجل في Audit Log، وتظهر النتيجة في التطبيق.
إذا ضغط رفض: لا Side Effect، ويُسجل الرفض.

هذا السيناريو وحده يختبر: التطبيق، API، Agent Core، LLM، Tool Calling، Read Action، Write Action، Human Approval، State Persistence، Resume، Verification، Audit Trail.

## 9. عقد v0
ملف V0_CONTRACT.md هو المصدر الوحيد للعقد، وهذه الوثيقة تلخصه فقط.
- الطلب: contract_version, request_id, conversation_id, input_type, message, attachments, client_context
- الرد: response_type (MESSAGE | TASK_STATUS | APPROVAL_REQUEST | RESULT | ERROR), task_id, status, message, data, error
- طلب الموافقة: task_id, action_id, idempotency_key, اسم العملية, وصف ما سيتغير, الأداة, المورد المتأثر, الوجهة, مستوى الخطورة, وقت انتهاء الصلاحية
- القرار: action_id نفسه + APPROVE / REJECT، لمنع تنفيذ موافقة على عملية مختلفة

## 10. Idempotency
كل عملية حساسة لها idempotency_key. ضغطتان على موافق، أو إعادة إرسال بسبب الشبكة، أو طلبان متزامنان: لا تنفيذ مرتين.

## 11. ثوابت الأمان
Least Agency، Tool allowlist، Path validation، موافقة بشرية لأي Write Action، Idempotency، Audit trail، الأسرار من env فقط، لا مفاتيح في التطبيق، التطبيق لا يتصل بمزود النموذج، مصادقة بين التطبيق والـCore.

## 12. Model Layer
لا Model Gateway في v0.1. واجهة صغيرة واحدة (ModelClient) ومزود واحد، مع إمكانية استبدال المزود لاحقًا دون تغيير بقية النظام. لا Framework جديد.

## 13. Memory و RAG
لا يدخلان في أول Slice إلا بالحد الأدنى. أول هدف: Input → Reasoning → Tool → Approval → Execution → Verification → Result. بعد نجاحه تُضاف الذاكرة والاسترجاع كطبقات مستقلة.

## 14. ما بعد v0.1 (بالترتيب)
1. n8n خلف الـCore: webhook موثّق ثم callback، مع تمرير task_id و action_id و idempotency_key.
2. Memory و RAG كطبقات مستقلة.
3. الصوت والصور في التطبيق.
4. غرفة العمليات: الواجهة الكاملة بالثيمات ولوحة الـworkflow الحية، فوق أساس شغّال.

## الشكل النهائي
Ahmed → Ahmed App → Core API → Agent Core + State Machine → Models / Tools / Retrieval → n8n / External Services → Verification + Audit → Ahmed App

الثابت في النظام: العقد + الحالة + الصلاحيات + الموافقة + التحقق + التدقيق.
المتغير: التطبيق، n8n، النموذج، وأدوات التنفيذ. كلها قابلة للتطوير أو الاستبدال لاحقًا دون إعادة بناء عقل الوكيل.
